# DVCC extension for the managed (Huawei) chargers, one folder per `dbus-systemcalc-py` version

The extension adds a charger stage to Venus OS's DVCC delegate (`delegates/dvcc.py` of
`dbus-systemcalc-py`): `com.victronenergy.charger` services that opt in (the Huawei driver) receive
`/Link/ChargeCurrent`, `/Link/ChargeVoltage`, `/Link/NetworkMode` and a `/Huawei/Heartbeat` every
3 s, from the budget that is left after the solar chargers; the Multi gets what the Huaweis made
subtracted. Design record: `../../docs/Design_Option1_DVCC_Patch.md`. The D-Bus paths, settings and
rules are identical on both versions; only the code they are grafted on differs.

| Folder | `dbus-systemcalc-py` | Venus OS | Device (test installation) | Installed |
| --- | --- | --- | --- | --- |
| `2.103-1/` | 2.103-1 | v2.92 | Cerbo GX | 2026-10-22 |
| `2.257-1/` | 2.257-1 | v3.85 | Raspberry Pi 5 | 2026-11-23 (port record: `../../docs/DVCC_Port_Venus_3.85_Assessment.md`) |

Find your version with `opkg list-installed dbus-systemcalc-py` (or the hash:
`sha256sum /opt/victronenergy/dbus-systemcalc-py/delegates/dvcc.py`, pinned as `PRISTINE_SHA` in each
`install.sh`). Any other version is refused by every installer; port the hunks first (below).

## What each version folder holds

| File | Content |
| --- | --- |
| `install.sh` | installer for **that version only** (SHA-256 pinned pristine, patched and module hashes): `check`, `install`, `rollback`, `guard` (boot-time, run by `/data/huawei/boot.sh`) |
| `patched-dvcc.py` | the complete replacement `delegates/dvcc.py`, generated by `apply_hunks.py` from the pristine file |
| `managedcharger.py` | the new `delegates/managedcharger.py` (`ManagedCharger`, `ManagedChargerSubsystem`) |
| `apply_hunks.py` | the hunks with their anchors: the source of truth; every anchor must match exactly once |
| `huawei-dvcc-<version>.patch` | the same change as a unified diff (`diff -u upstream/delegates/dvcc.py patched-dvcc.py`) |
| `upstream/` | the pristine package as shipped on the device (MIT, Victron Energy), with its `tests/` from the matching upstream commit, used as the test harness |

On the device all three runtime files live in **`/data/huawei/patch/`** (same path on every
platform; the files are the ones of the device's version). Backups go to
`/data/huawei/backup/dvcc.py.<version>.orig`, the record to `/data/huawei/patch.manifest`, and an
unsupported version leaves `/data/huawei/dvcc_unsupported`, which keeps the driver inhibited.

Differences of the 2.257-1 port, apart from the anchors: `ManagedCharger` subclasses the new
`BaseCharger`/`Networkable` classes (the import sits right before `class Dvcc` so the classes exist
when `managedcharger.py` loads); the budget subtracts the whole stock charger stage
(`ChargerSubsystem.smoothed_current`: solar, inverter/chargers, alternators, DC gensets), not just the
solar chargers; a Dynamic-ESS maximum charge power (`internal_maxchargepower`), new in 2.257-1, caps
the Huawei budget like the Multi's.

## Tests

```sh
python src/patch/tests/run_tests.py              # 33 managed-charger tests on both versions
python src/patch/tests/run_tests.py 2.257-1      # one version
python src/patch/tests/run_tests.py --upstream   # plus each version's complete upstream suite on the patched tree
```

`tests/managedcharger_test.py` is shared by both versions. Each run assembles a throw-away copy of
`upstream/` with the two patched files laid over it, so the checked-in trees stay pristine. On
Windows the stand-ins in `tests/win-shim/` replace dbus-python and GLib (the harness's own mock
D-Bus does the work). 2026-11-23: 33/33 on both; the upstream suites fail the same single test on
pristine and patched trees (`test_13_derive_battery` needs a running `localsettings`).

## Porting to another version

Copy the pristine tree into `<version>/upstream/` (plus `tests/` from the upstream commit whose
files hash-match the device), copy `apply_hunks.py` and `managedcharger.py` from the nearest
version, fix the anchors until all 15 hunks apply exactly once, regenerate `patched-dvcc.py` and
the `.patch`, run the tests, then derive `install.sh` with the three new hashes. Install with
`install.sh check` (must say `pristine`) and `install.sh install`; the driver has to be restarted
once afterwards (`svc -t /service/huawei-charger`) so it finds `/Control/ChargerChargeCurrent`.

## Where the chargers show up

- Venus GUI: Device List on both platforms; the overview tile (`../classic-gui/`) needs
  `/Dvcc/Chargers/Active` from this extension and is visible while a Huawei is switched on and able.
- VRM: the charger is in the installation's Device List and its values (voltage, current,
  temperature, AC input current and power, state, mode, error, alarms) in the Advanced widgets, as
  for Victron's own AC chargers; vrmlogger logs `com.victronenergy.charger` services of any
  ProductId. The production VRM dashboard has no box for AC chargers (Victron's Skylla and Phoenix
  Smart chargers are not drawn either); the dashboard that VRM is rolling out with Venus 3.8x draws
  AC chargers as DC-source blocks under the battery. That part is VRM's, not this project's.
