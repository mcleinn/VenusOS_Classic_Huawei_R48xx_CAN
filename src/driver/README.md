# Huawei charger driver for Venus OS (Cerbo GX): engineering notes

Detailed, dated notes on what the driver does and why, kept as the work progressed. For an
overview, the hardware list and the installation steps start with the repository `README.md`.

Target: Venus OS v2.92, Python 3.8, no python-can. Two Huawei rectifiers on one bus: **R4875G5**
(69 A nominal, serial 708A85B00972) and **R4875G1** (75 A nominal, serial E4308598A003). The project
folder and older documents say R4850G2, which was the assumption before the e-labels were read on
2026-10-25.

## Topology this driver is written for

- The Cerbo's two VE.Can RJ45 sockets are **one CAN interface** (`can0`), electrically paralleled. One rectifier is plugged into each socket; both are on the same bus.
- Therefore: **one driver process, one SocketCAN interface, N modules** (N = 2 here) identified by serial, **one D-Bus charger service per module**. There is never a second process or a second interface for the second charger.
- The bus ends are at the rectifiers, so the 120 Ω terminators belong at each rectifier end. Nothing is terminated at the Cerbo; the VE.Can sockets are pass-through.
- RJ45 wiring per Victron VE.Can pinout: pin 7 = CAN-H, pin 8 = CAN-L, pin 3 = GND. On the Huawei edge connector the pair is top/white = CAN-L, bottom/black = CAN-H. Verify on the bench (Phase B, B0.3) before relying on it.
- Addresses on the Huawei bus are negotiated by the modules (lowest serial = address 1) and can change when a module restarts. The driver keys everything by serial and re-learns the serial-to-address map from the bus; it never stores an address as identity.

## Control build of 2026-11-01 (what no longer waits for the load tests)

Built against simulated units with the verification flag forced in the test fixture; since 2026-11-04 the flag in the code is True (see 0.9-verified above) and the test benches ask for control explicitly (`control=True`). Historical text follows: the flag in the code was still False, so the running driver stays telemetry-only.

1. **Acknowledgement handling.** A set frame without an ack within `ACK_TIMEOUT_S` (1 s) or with the 0x21 error byte faults the unit; the governor then requests zero, the commander writes it, `/Alarms/SetpointError` = 2. The fault is held `FAULT_HOLD_S` after the last cause; a fault caused by a disconnect is cleared when the unit returns.
2. **Verification by measurement.** `SETTLE_S` after an acked non-zero limit, a measured current above the limit by more than 2 A or 10 % is an "overshoot" fault, zeroed at once. A wrong scale policy shows up on the first ampere. Current below the limit is normal.
3. **Zero-default check.** The first burst a unit ever sends this process arrives before any write (quiet start, and the commander writes nothing until then); its 0x76 is the stored default (measured on the R4875G5). Not zero means the unit is not commissioned: `/Huawei/DefaultLimitOk` = 0 and it is never written to, not even a zero.
4. **Fail-safe tick.** Any exception in `tick()` or `on_frame()`: zero to every commanded unit, services off-line, no further polling, the process exits with code 5 and daemontools restarts it into a fresh quiet start (`engine.failsafe`, `EngineFailure`).
5. **Keep-alive and shutdown** proven end to end: unchanged requests re-sent every `RESEND_S`, zero as the last frame on exit.
6. **Two units:** independent allocations, one unit unplugged, one faulting, DVCC taking the budget away (SOC ceiling), a unit returning after a restart.
7. **Operator paths:** `/Mode` off (zero within a tick, no ramp down), cap lowered while charging, DVCC heartbeat loss.
8. **Fixture:** `test_control_path.VerifiedCase` flips the flag; `test_gate_closed_without_the_flag` runs the same stimulus with it off and sees no set frame.

Explicit zeros: with the flag on, the commander writes an explicit 0 A on-line limit to every commissioned unit as soon as it is seen, so the on-line limit is known rather than inherited.

**Output-enable sequence (added 2026-11-01; answered the same day, `evidence_output_enable_probe.txt`).** A unit powered up with no controller keeps its output stage off (2.6 V on the terminals). Probed from the Cerbo on the cold-started unit 1: the standby register 0x32 only toggles status bit 9 and does not switch the output; **the first non-zero on-line current limit switches it on** (status bit 27, published as `/Huawei/OutputOn`), and a 0 A limit cannot charge the output capacitors, so the terminals show the residual voltage, not the setpoint. The policy therefore stays `"none"`; the alternatives remain in the code for other models. `driver.json` carries `"output_enable"`: `"none"` (default, writes only 0x00/0x03), `"standby0"` (on = 0, off = 1, the community reading) or `"standby1"`. With a policy set, the commander writes the "on" value before the first non-zero limit (order voltage, standby, current), repeats it with the keep-alive, and writes "off" when the request drops to zero and on shutdown. Tests: `test_control_path.TestOutputEnable`.

Output gate (as built; the flag is True since 2026-11-04, the run script's `--control` is the switch now): no 0x80 set frame can leave the process while `protocol.VERIFIED` is False. The engine then runs the telemetry-only commander, the governor reports "protocol unverified (Phase B pending)" in `/Huawei/LimitingReason`, `/State` stays 0 so the patched DVCC allocates nothing and the overview tile stays hidden. Tests assert that no set frame crosses the virtual bus under full DVCC/operator stimulus.

What Phase B still feeds back into the code: the calibrated scale per serial (`driver.json`, replacing `conservative`), the remaining `UNVERIFIED` items in protocol.py (then `VERIFIED = True` with the evidence files named in the commit), `RAMP_UP_A_PER_S`/`RESEND_S` in control.py, and the freshness windows in modules.py if the measured timings differ.

## Rules carried over from the brief

Read-only Cerbo until authorised; no charger output before the Phase B zero-current fallback has passed on both units; missing or stale data never means unlimited charging; commanded and measured values are kept apart.

## Verified on the live Cerbo with the stub (2026-10-22, Phase A report §8b)

- Two services in one process need **one private D-Bus connection per service** (`dbus.SystemBus(private=True)`); dbus-python exports a single root object per connection. The stub does this now.
- Instances: both services request `charger:290`; localsettings keeps 290 for the first serial and hands out 291 for the second. Instances are stable per serial across restarts.
- systemcalc sums the services into `/Dc/Charger/Power` immediately; stock DVCC writes nothing to `/Link/*` or `/Mode`.
- **Patched DVCC is installed since 2026-10-22** (see `Design_Option1_DVCC_Patch.md` §12). The driver must publish, besides the brief's paths: `/Settings/ChargeCurrentLimit`, `/Link/ChargeCurrent|ChargeVoltage|NetworkMode` (writeable), `/Huawei/Heartbeat` (writeable; DVCC writes a changing counter every 3 s while in control, this is the liveness signal, not `/Link/ChargeCurrent`, because vedbus swallows unchanged SetValues), `/State` ≠ 0 whenever the unit can deliver (0 = inhibited, gets 0 A), and a `/Mgmt/ProcessName` containing "huawei". Secondary check: `/Control/ChargerChargeCurrent` on `com.victronenergy.system` must exist and be 1. `/Dvcc/Chargers/SocInhibit` = 1 means the DVCC SOC ceiling (90 %/85 %) holds the budget at 0.
- GUI: a charger service shows in the Device List as an AC charger (`PageAcCharger.qml`). It has a user-writable Switch on `/Mode` (1 = on, 4 = off); the driver treats a `/Mode` write as an operator enable/disable request that never bypasses the heartbeat, caps or inhibit. Publish `/Ac/In/L1/I` and `/Ac/In/L1/P` (shown in GUI and VRM); do not publish `/Ac/In/CurrentLimit` (the GUI would offer a spin box for a limit the driver does not implement).
- VRM logs `/Dc/0/*`, `/Ac/In/L1/*`, `/Mode`, `/State`, `/ErrorCode`, `/Alarms/*` and the identity paths. `/Huawei/*` and `/Link/*` stay local.
- VRM does not draw a `com.victronenergy.charger` service on the dashboard (verified with the stub, 2026-10-22). For visibility the driver also publishes, per unit, a display-only `com.victronenergy.dcsource.huawei_<serial>` service (`/Settings/MonitorMode` −2 = "AC charger", `/Dc/0/Voltage|Current|Power` mirrored from the charger service, `/CustomName`, `/Serial`, `/ProductId`, `/Alarms/*`; see `--dcsource` in the stub). VRM draws it and labels it "AC charger", which the user accepted (Phase A report §8f). It is ignored by DVCC, by the DC-system estimate and by kWh accounting on v2.92, so it has no control effect. Allocate it with its own device instance (the stub got 300/301) and keep its heartbeat/availability tied to the charger service so a stale value never lingers after the unit drops off CAN.

## Venus settings and autostart

**No Venus setting enables the driver.** Settings → Services → VE.Can port only chooses which Victron process owns `can0` (profile 0 = Disabled, 1 = VE.Can 250 kbit/s, 3 = CAN-bus BMS 500 kbit/s, …). There is no entry for third-party drivers. The profile must stay **Disabled**; the driver's start script checks `/Settings/Canbus/can0/Profile == 0` and refuses to start otherwise, then configures the link itself (`ip link set can0 up type can bitrate 125000 restart-ms 100`).

**Autostart is required and must be added** (Phase A report §8c): nothing starts from `/data` except `/data/rc.local`, and `/service` is rebuilt from `/opt/victronenergy/service` at every boot. Planned mechanism, standard for `/data`-resident add-ons on Venus OS:

```
/data/huawei/service/run          # exec python3 /data/huawei/src/driver/main.py (with softlimit like the stock services)
/data/huawei/service/log/run      # exec multilog t s25000 n4 /data/huawei/log   (log on /data, not on tmpfs)
/data/rc.local                    # + ln -sfn /data/huawei/service /service/huawei-charger
```

`svscan` picks up the new symlink within about 5 s, supervises the process, restarts it on crash (1 s back-off) and gives `svc -d/-u/-t /service/huawei-charger` for stop/start/restart. The line is appended to the existing `/data/rc.local` (which already starts the user's cell-voltage logger); the file is not replaced. Firmware updates do not touch `/data`, so the driver survives them; only the DVCC patch in `/opt` would need re-applying, guarded by the hash check already described in the design record. Installing this is a Phase C action and waits for authorisation; the stub is never autostarted.

- Overview tile (2026-10-22): the Remote Console shows a "Huawei" tile while `/Dvcc/Chargers/Active` > 0, which the patched DVCC derives from `/Connected` == 1 and `/State` != 0 on the charger services. The driver must therefore publish State 0 whenever a unit is off, inhibited or faulted, and a non-zero state (e.g. 252 external control / 3 bulk) only while the unit can actually deliver. The tile shows each unit's `/Dc/0/Power` (or `/Dc/0/Voltage` x `/Dc/0/Current` if the driver does not publish power), so those must be real measurements; unit order on the tile is by service name, i.e. by serial.
